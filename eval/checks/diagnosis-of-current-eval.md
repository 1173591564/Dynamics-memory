# 动力学记忆系统的评测设计（研究稿 v1）

> 适用对象：Dynamics-memory（C/M/A 三池、V 衰减 + 信用、tension → judge、salience、recall_miss 拉取回路、L0 日志）
> 日期：2026-09
> 复现脚本：`dm-run/eval/*.py`（第 2 节的数字都能用它们重跑）

---

## 0. 结论先行

1. **被测对象是一个"过程"，不是一个"库"。** 系统状态依赖路径：检索会改状态，信用会改排序，拉取回路会改数据。所以评测单元应该是"一条带时间戳的事件流 + 流上按时间点插入的探针"，而不是一堆独立的问答对。
2. **现在的评测已经测错了方向。** 我在仓库现有的 sim 上做了复核（第 2 节），发现 3 个问题：
   - **口径错杀机制。** 聚合记忆（tension 的正确产物）被 ground truth 判为"不相关"。修正后，冲突相位 recall 从 0.627 变成 **0.871**，结论从"tension 有害"反转为"tension +10.6pp"。
   - **机制没被触发。** `abl_no_shadow`、`abl_no_capacity` 与 `ours` 三位小数完全相同。真实日志运行中 merge、resolve、revive、demote 全为 0。
   - **只算召回、不算污染。** flat 的 recall 最高（0.917），但在 69% 的漂移查询里，它把旧值和新值一起注入；ours 只有 4%。
3. **金标准应当是"未来需求"加"事实有效期"，而不是"答对了没有"。** 遗忘本身是功能，需要区分两种遗忘：
   - **失效**：被取代或被撤回，这种应当遗忘；
   - **过时**：仍然为真，但不再被需要，这种可以遗忘。

   前者用双时态事实账本判定，后者用流里的未来需求判定（Belady 式 oracle）。
4. **一个总分没有意义。** 应该分层报告：漏斗各阶段的损失（尤其是本系统独有的"存活"阶段），动力学指标（更新延迟、保留曲线、需求校准），以及结果分类（答对现值 / 旧值 / 混淆 / 编造 / 合理弃答）。报告时使用不对称效用。
5. **统计功效是硬约束。** 现在的连续性评测 n=13：
   - memory 与 flat 之差为 +0.69，95% CI [−0.06, +1.45]，**不显著**；
   - 5 个特性集的 memory 分数中，4 个逐题完全相同。

   要检出 0.1 的二值差异，需要约 340–560 个探针，分布在 ≥20 条流上。流的数量比每条流的探针数量更重要。

## 1. 为什么传统基准不适合

| 传统基准的隐含假设 | 这个系统的实际情况 | 后果 |
|---|---|---|
| 记忆是被动存储，评测是只读的 | `retrieve()` 会改状态：shortlisted++、suppressed_by、新增 tension、shadow pending、archive revive、thin_recall 信号；`qa_real` 的考题还会走 `feedback()` 和 `step()` 记账 | 考题本身成了训练信号（观察者效应），后面的题会变简单 |
| "记住更多"更好 | 遗忘、降级、归档是设计目标；Supersede 发现，有界自维护记忆在 LongMemEval 知识更新上从 92% 掉到 77%，给 24 倍容量也补不回来 | 只算召回会系统性地偏向囤积（flat） |
| 每题独立 | V 的半衰期约 35 步（λ=0.02），idle 归档 50 步，tension_delay 20 步 | 流短于机制时间尺度时，机制根本不触发，消融测的都是噪声 |
| 错误是对称的 | 陈旧答案、混淆答案比"不知道"危害大；Sufficient Context 显示，额外上下文会提升幻觉、降低弃答 | 1–5 分量表奖励"敢答"（见 D6） |
| 静态语料 | 本系统有闭环：信用 → 排序 → 曝光 → 信用；recall_miss → 拉取 → 新记忆 | 离线日志只能做开环评测（off-policy 问题，见 6.3） |
| 基准键值可信 | LoCoMo 审计显示，6.4% 的答案键有误，LLM 裁判接受 63% 的含糊错误答案；LongMemEval 已能整体塞进上下文 | 在公开基准上"刷分"不能说明动力学有效 |

文献中与这个方向最接近的工作：

- **MemoryAgentBench**（ICLR 2026）的四能力框架，其中"冲突解决"采用增量注入；
- **HaluMem** 的操作级评测（抽取 / 更新 / 问答分开打分，更新准确率 < 26%，误差逐级传播）；
- **Memora / FAMA** 的"应记住 + 应遗忘"双判据；
- **PI-LLM** 的"更新次数 → 准确率对数线性下降"曲线；
- **MemoryArena** 的"召回高 ≠ 行动对"；
- **LongMemEval** 的 indexing / retrieval / reading 三阶段分解。

这些工作都各自只覆盖了一个侧面，没有一个评测"有自身动力学的记忆"。本文把它们组合起来，并补上动力学专属的部分。

## 2. 对现有评测的诊断（本仓库实证）

### D1 评分口径错杀机制：聚合记忆被算作 miss

`sim/world.py` 中的 `relevant()` 要求 `belief_id == target` 且 `value` 有效。tension 产生的聚合体的 value 形如 `agg:a+b`，永远判为无效。它既不算命中，还会被当作污染。然而，冲突相位（同一实体、不同作用域）的正确行为，恰恰是把两个版本连同各自的作用域一起给出。

我做了一个反事实重评分：只要聚合体的成员里包含目标且有效，就算作命中。结果如下（10 seeds，T=220，冲突相位共 1569 个查询；脚本 `rescore_aggregate.py`）：

| preset | all 原口径 | all 修正 | 冲突相位 原口径 | 冲突相位 修正 |
|---|---|---|---|---|
| **ours** | 0.792 | **0.881** | 0.627 | **0.871** |
| decay_only | 0.837 | 0.871 | 0.743 | 0.835 |
| abl_no_tension | 0.833 | 0.833 | 0.765 | 0.765 |
| abl_no_dedup | 0.849 | 0.896 | 0.781 | 0.910 |
| abl_no_twopool | 0.770 | 0.827 | 0.620 | 0.778 |
| flat | 0.917 | 0.917 | 0.973 | 0.973 |

**教训：** 必须先确认评测口径能识别出机制的"正确输出形态"，再比较机制的好坏。建议把这一条写进 CI，做成一个"口径单测"：人工构造一个理想的聚合输出，确认它得满分。

### D2 机制覆盖率不足：消融测的是空气

- `abl_no_shadow` 和 `abl_no_capacity` 在所有相位、所有指标上与 `ours` **逐位相同**。原因是 shadow credit 与容量淘汰在这个流里从没改变过任何一次检索结果。
- 真实日志运行 real-run-v2（106 个 unit）中：
  - 各操作计数为 promote 161、evict 153、archive 92、tension 7，**merge、resolve、revive、demote 全为 0**；
  - M 池的平均驻留时间约为 8×106/161 ≈ **5 个 unit**。所谓"长期池"实际上是一扇旋转门。
- **结论：** 每次评测都必须附一张机制触发表（见 5.3.6）。某个机制的触发次数低于阈值时，对应的消融结论一律标为"不可判定"。

### D3 天花板效应

value-modes-v3 中，所有特性集的 `latest_update=1.0`、`stale=0.0`。说明更新测试太容易：旧值与新值措辞不同，嵌入空间直接可分。需要加入以下难度维度：

- **措辞漂移**：新旧值用相同措辞；
- **隐式更新**：没有"改成"之类的字眼；
- **部分更新**：只改一个字段；
- **回滚**：A→B→A；
- **多次更新**：按 PI-LLM 做 1、2、4、8、16 次，画出曲线。

### D4 统计功效

qa-cont-v4 共 n=13，1–5 分量表。配对分析结果（脚本见第 7 节）：

| 比较 | 均差 | 95% CI | Wilcoxon p | 80% 功效下的 MDE |
|---|---|---|---|---|
| memory vs none | +1.15 | [+0.38, +1.93] | 0.014 | 1.07 |
| memory vs flat | +0.69 | [−0.06, +1.45] | 0.094 | 1.05 |
| 特性集 full vs p01 | 0.00 | [−0.49, +0.49] | 1.0 | 0.68 |

此外：

- r1 / r12 / r123 / full 的 memory 逐题分数**完全相同**；
- flat 和 none 臂的回答在各特性集之间也相同（命中了缓存）；
- **结论：** 现有数据只能支持"有记忆好于没有"，不能区分 memory 与 flat，更不能区分特性集。

### D5 考题污染状态

- `qa_real.py:167–183`：考题先 `retrieve`，再 `feedback`，然后 `step`。
- `qa_continuity.py:209–249` 也一样。

所以前一道考题的信用会影响后一道考题，评测顺序本身就是一个混杂变量。

### D6 裁判口径奖励"敢答"

| 臂 | 连续性（1–5 分） | 关键点命中 | 关键点编造率 |
|---|---|---|---|
| memory | 3.2–3.3 | 0.25–0.27 | **0.62–0.69** |
| flat | 2.6 | 0.175 | 0.77 |
| none | 2.15 | 0.125 | **0.31** |

记忆让回答者更"有底气"地编造。这一点与 Sufficient Context 的发现一致。整体印象分会掩盖这种伤害。

### D7 漏斗已有雏形

poolcov 显示，关键点在池中的覆盖率为 0.371，在 top-5 上下文中只有 0.164。也就是说：

- 约 63% 的关键点在抽取阶段就丢了；
- 剩下的约一半又在检索阶段丢掉。

但这个分析缺了"存活"这一段，也就是入池之后，被衰减、归档或淘汰掉的那部分。这恰恰是本系统独有的损失。

### D8 只算召回、不算污染

只看漂移过的 belief（769 个查询；脚本 `stale_in_context.py`）：

| preset | 含现值 | 含旧值 | 现值且无旧值 | 平均注入条数 |
|---|---|---|---|---|
| ours | 0.960 | 0.040 | **0.960** | 1.13 |
| flat | 0.948 | **0.692** | 0.308 | 5.00 |

flat 的高 recall 是囤积的结果。只要按 FAMA 的思路引入"应遗忘"判据，排序就会反过来。

## 3. 设计原则

1. **评测轨迹，而不是评测快照。** 每个探针都带两个时间：
   - **question time**：什么时候问；
   - **knowledge time**：答案的有效区间（参考 StreamingQA 和 Graphiti 的双时态 t_valid / t_invalid）。

   同一个问题在不同时间点有不同的正确答案。
2. **金标准 = 事实账本 + 未来需求。**
   - 账本判定"什么是真的"。
   - 流里的未来查询判定"什么值得留"：Anderson & Schooler 发现，环境中的需求概率对新近度和频率都呈幂律；Belady MIN 给出离线最优淘汰的上界。
3. **每个机制至少对应一个敏感指标，外加一个覆盖率闸门。** 见第 5 节的"机制 → 指标"对照表。
4. **探针和负载分离。**
   - **被动探针**：dry-run，对引擎做快照，读完即回滚。它测量状态。
   - **主动探针**：本身就是负载的一部分，会产生信用。它测量闭环。

   两类探针分开计分。
5. **给结果分类，而不是给一个分数。** 分类见 5.4。在分类之上用不对称效用加权，并同时报告每个类别的比例。
6. **统计先行。** 流级聚类标准误、配对差、预注册、功效分析，以及按流划分 dev/test（参考 Miller《Adding Error Bars to Evals》）。
7. **合成数据要被真实统计校准，并做外部效度检验。**
   - 生成器参数（需求过程、更新率、会话间隔）从真实 L0 日志拟合。
   - 用"合成排名 vs 真实排名"的 Kendall τ 检验合成集是否可信。
   - 渲染对话用的 LLM 与系统内部抽取用的 LLM 要来自不同模型族，以免同源偏差。

## 4. 评测集：事实账本 + 事件流 + 探针

### 4.1 账本 schema

一条流 = 一个账本 + 按时间排列的事件 + 探针。

```yaml
facts:
  - id: F12
    subject: "构建工具"
    value: "webpack"
    scope: {module: "web"}            # 作用域：用于同实体、不同作用域的"矛盾"
    t_valid: [3, 58]                  # 双时态有效区间（turn 索引）
    wall_valid: ["2026-03-02", "2026-04-11"]
    superseded_by: F31                # 更新链
    depends_on: []                    # 级联依赖
    importance: high                  # 用于 salience / 长间隔重要稀有
    kind: decision                    # decision / preference / status / method / fact / transient
  - id: F31
    subject: "构建工具"
    value: "vite"
    t_valid: [58, null]
    supersedes: F12
    evidence: {turn: 58, explicitness: implicit}   # explicit / implicit / inferred
  - id: F40
    subject: "dev 启动命令"
    value: "npm run dev -- --port 5173"
    depends_on: [F31]                 # F31 变了，F40 应随之失效或更新（RippleEdits/MQuAKE）
events:                               # 渲染前的抽象事件
  - {t: 58, type: update, fact: F31, surface: "那就别折腾了，直接切 vite 吧", gap_before: "3d"}
probes:
  - {t: 90, type: stale_trap, ask: "webpack 配置里的 alias 怎么写？", gold: F31,
     harmful: [F12], expect: "指出已切到 vite", mode: passive}
```

### 4.2 世界动力学生成器（扩展 `sim/world.py` → `sim/ledger_world.py`）

生成器包含以下过程：

- **需求过程。** 每个事实的被提及、被需要，按幂律到达间隔生成（带 Zipf 流行度）。**不要用泊松分布**：衰减函数谁优谁劣，取决于环境的真实统计（Anderson & Schooler）。
  - 参数从真实日志中 `mentions` 的再提及间隔拟合，用 MLE 拟合截断幂律或对数正态，并与指数分布做 Vuong 检验。
  - 半衰期回归（HLR，p = 2^(−Δ/h)）可以作为"需求预测器"基线。
- **更新类型：**
  - 显式替换；
  - 隐式替换（语气里带出来的）；
  - 部分字段更新；
  - 回滚（A→B→A）；
  - 撤回（"之前说的那个作废"，属于 Absence 类；MEME 显示这一类的得分只有 0.01）；
  - 多次连续更新（PI-LLM 曲线）。
- **级联。** 通过 `depends_on` 形成依赖图，上游更新时下游失效。MEME 的 Cascade 类得分只有 0.03。
- **作用域矛盾。** 同一主体在不同作用域下取不同值，例如 web 用 vite、docs 用 webpack。两者都为真，考的是 tension 的 collision 判决与 contested 共同服务。
- **未决冲突。** 用户自己也没定，正确回答是"诚实地呈现两个选项"。
- **临时状态。** 例如"我现在在调这个 bug"。它半天后就应该失效，不应在一周后被注入。
- **重要但稀有。** 只提过一次，但代价很高的约束，例如"不要动 prod 数据库"，间隔 100 个以上 turn 之后才需要。考的是 salience 与归档复活。
- **干扰负载。** 在需要之前插入 k 条相似但无关的事实，k ∈ {0, 4, 16, 64}，画出干扰曲线。
- **会话结构。** 会话间隔服从真实分布（从 L0 的 wall-clock 拟合）。连续性探针放在长间隔之后的会话开头。
- **措辞漂移。** 新值沿用旧措辞，或者提问用旧措辞问新值。这一项用来打破 D3 的天花板。

### 4.3 渲染

- 用 LLM 把抽象事件渲染成开发对话。
- 显式度分三档：explicit、implicit、inferred。每个探针都记录它依赖的事件属于哪一档，这样可以把"系统没抽到"与"数据太隐晦"区分开。
- 渲染模型与系统内部的抽取 / judge 模型来自不同模型族。同一条流再用第二个模型族渲染一遍，做交叉检验（参考 *Lost in Simulation*：换一个用户模拟 LLM，τ-bench 成功率最多差 9pp）。
- 渲染后，由人工或另一个 LLM 核对账本：每个事件是否确实能从文本中推出来，否则剔除这个事件。

### 4.4 探针类型（12 类）与目标机制

| # | 探针 | 例子 | 主要考验的机制 | 正确行为 |
|---|---|---|---|---|
| 1 | 当前值 | "我们用什么构建工具？" | 抽取、检索 | 答出现值 |
| 2 | 陈旧陷阱 | 用旧措辞问 webpack alias | supersede、衰减、dedup | 纠正为现值，不注入旧值 |
| 3 | 历史追问 | "当时为什么从 webpack 换掉？" | 归档、历史保留（失效 ≠ 删除） | 给出变更和原因 |
| 4 | 作用域矛盾 | "docs 用什么构建？" | tension→collision、contested | 按作用域分别回答 |
| 5 | 未决冲突 | "定了用 A 还是 B 吗？" | tension→contradiction 未决 | 诚实呈现分歧，不擅自拍板 |
| 6 | 撤回 / 缺失 | "那个 Redis 缓存方案进度？"（已作废） | 撤回处理、弃答 | 说明已作废，不编造 |
| 7 | 级联 | "dev 启动命令是？"（上游已换） | 依赖传播 | 不给出失效的派生值 |
| 8 | 长间隔、重要稀有 | 第 150 turn 问第 5 turn 的约束 | salience、归档复活、衰减参数 | 召回 |
| 9 | 临时状态不注入 | 一周后问无关问题 | 衰减、idle 归档 | 不注入过期的临时状态 |
| 10 | 连续性 | 长间隔后"接着搞" | 会话级摘要、近期性 | 复述正确的进行中事项 |
| 11 | 修复 | 同一信息第二次被问 | recall_miss → 拉取回路 | 第二次答对 |
| 12 | 干扰负载 | 同一问题在 k 条干扰下 | τ_sim 抑制、θ 门 | 曲线下降尽量平缓 |

每个探针都要标注：`mode`（被动或主动）、依赖事件的显式度、需要跨越的时间 lag、干扰数 k、金事实，以及有害事实（harmful）。

### 4.5 三条数据轨道

| 轨道 | 规模（建议） | 作用 | 可控性 | 外部效度 |
|---|---|---|---|---|
| **A 合成账本流** | 30–60 条流 × 150–400 turn × 15–25 个探针 | 主评测、消融、功效 | 高（精确金标准） | 需要校准 |
| **B 真实日志标注** | 3–5 条 L0 日志（脱敏） | 校准生成器；检验合成→真实的排名一致性 | 中 | 高 |
| **C 可执行编码轨** | 10–20 个序列 | 衡量"记忆 → 行动"的终极效用 | 高 | 高 |

- **轨道 B 的标注流程：** LLM 先从日志中提议账本条目，人工核对（AutoNuggetizer 的结论是"人工 nugget + LLM 判定"性价比最好）。标注前务必脱敏，参见之前指出的 `experiments/out` 隐私泄漏。
- **轨道 C 的构造：**
  - 用固定的 fixture 仓库，事件序列里埋入决策和变更（参考 DreamBench-SWE 的三会话陷阱）；
  - 用 CSPRNG token，防止模型凭先验猜中；
  - 用隐藏测试打分。

  要注意：VibeMemBench 中 12 个记忆 × 求解器组合里有 11 个不优于关闭记忆。这一轨很可能得到零结果，而这本身就值得报告。

## 5. 指标体系

### 5.1 漏斗归因（主诊断）

对每个探针 p 及其金事实 f，按以下阶段逐一判定：

```
said ─▶ logged ─▶ extracted ─▶ SURVIVED ─▶ retrieved ─▶ used-correctly
 (L0)    (unit)    (C 池条目)   (问的时刻仍存活、  (进上下文)   (答案判定)
                               可见、版本正确)
```

- 每个阶段的条件通过率为 `P(stage_i | stage_{i-1})`。报告每个阶段的损失份额。
- 另外单独列出一条**恢复路径**：没有通过 retrieved，但经 recall_miss → 拉取之后在下一轮通过。
- **存活**是本系统独有的阶段。它的失败原因要细分到机制：
  - V 衰减到 θ 以下；
  - idle 归档；
  - 容量淘汰；
  - 被 τ_sim 抑制；
  - 被错误合并；
  - 版本错误，即 supersede 没有发生。
- 判定可以精确完成：引擎有完整的操作日志，账本给出金事实。
- 这是把 LongMemEval 的三阶段、HaluMem 的操作级评测扩展成六个阶段，重点补上"存活"。

### 5.2 检索层（精确金标准，不需要 LLM）

| 指标 | 定义 |
|---|---|
| Valid-support@ctx | 上下文里有 ≥1 条支持现值的记忆（聚合体的成员也算） |
| Stale-in-context | 上下文里含 harmful 事实（已失效的版本或派生值）的比例 |
| Clean-support | 有现值且没有旧值的比例（D8 里 ours 0.96，flat 0.31） |
| FAMA_ret | `max(0, MPA − λ·(1−FAA))`，λ 建议取 1–2 |
| Context precision | 注入内容中与账本相关的 token 占比 |
| Churn | 同一问题换措辞后，上下文集合的 Jaccard 距离 |

### 5.3 动力学层（本系统的核心，传统基准没有）

1. **更新延迟（生存分析）。**
   - `L_serve`：从更新事件到新值第一次被正确服务，所经过的 turn 数。
   - `L_purge`：从更新事件到旧值不再被注入，所经过的 turn 数。
   - 用 Kaplan–Meier 估计。没发生的记为右删失，不能丢弃。
2. **保留曲线。** 按事实类别和重要度分组，在 log(lag) 轴上画出"需要时可被服务"的概率，报告 AUC。PI-LLM 的 IES 用的是同一种思路。
3. **需求校准。** 把 V 看作对"未来 H 步内是否被需要"的预测，报告 AUROC 和可靠性图。H 取 {10, 35, 100}，其中 35 ≈ 半衰期。这是在直接问：V 这个量本身是否合理。
4. **缓存视角。**
   - `V ← V·e^(−λ) + η·hit` 在形式上就是 LRFU 的 CRF（Lee et al. 2001）。所以 M 池应当与以下策略比较：LRU、LFU、LRFU（扫 λ）、ARC、Belady MIN（需求已知的上界），以及只追加（append-only）。
   - 归一化得分：`(sys − LRU) / (OPT − LRU)`。
   - 注意：记忆条目长度不同时，MIN 只是一个松上界。
5. **池动力学健康度：**
   - M 驻留时间分布（现在约为 5 个 unit）；
   - promote/demote 抖动率（同一条记忆在 W 步内往返的次数）；
   - 活跃池规模随时间的斜率（immigration stress 中约为 −0.11）；
   - 曝光 Gini 系数；
   - 新的重要记忆第一次被服务所需的时间。这用来检测"富者愈富"，fresh_alpha 正是起探索奖励作用的。
6. **机制覆盖率（效度闸门）。**
   - 列出每次运行中各操作的计数：promote、demote、evict、archive、revive、merge、tension、各类 judge 判决、resolve、shadow credit、pull。
   - 对每个消融，报告"该机制改变了多少次检索结果"，即 decision-flip 数。
   - flip = 0 时，该消融判为不可判定（对应 D2）。

### 5.4 回答层

| 类别 | 判定 | 效用（示例） |
|---|---|---|
| correct-current | 答出现值 | +1 |
| correct+history | 现值加上正确的变更史（针对第 3 类探针） | +1 |
| honest-contested | 如实呈现未决冲突（针对第 5 类探针） | +1 |
| abstain-ok | 金标准就是无或已撤回，系统弃答或说明作废 | +1 |
| abstain-bad | 有金标准却弃答 | 0 |
| stale | 答出旧值 | **−2** |
| conflated | 新旧混杂，或张冠李戴 | −1.5 |
| fabricated | 答出账本里不存在的内容 | **−2** |

- 报告各类别的比例和期望效用。效用权重可以做敏感性分析（扫描 stale 的惩罚权重）。
- **选择性回答：** 同时报告 coverage–risk 曲线（Sufficient Context 建议的 selective generation）。
- **判分方式：** 采用"人工 nugget + LLM 判定"（AutoNuggetizer/TREC 2024 RAG 的结论）。
  - 裁判上线前先做压力测试：人工植入陈旧、含糊、编造三类错误答案，要求裁判识别率 ≥ 90%。
  - 背景：LoCoMo 审计中，裁判接受了 63% 的含糊错误答案。
  - 裁判与被测系统不使用同一个模型。

### 5.5 闭环层（拉取回路、信用）

- **Repair yield：** 第一次失败的探针中，第二次询问成功的比例。它必须与关闭回路的反事实版本相减：`yield(loop) − yield(no-loop)`。
- **Time-to-repair、False-repair rate：** 后者是拉取回来的"修复"本身有误的比例。
- **Cost per repair：** 每次成功修复消耗的 LLM 调用数和 token 数。
- **Recognizer 质量：** 以金标准"记忆是否被使用"标签，报告"被使用"判定的 P/R。信用回路的偏差源头就在这里。
- **Propose 溯源精度：** 提议的内容是否被源 unit 真正支持。现在只检查了源 unit 是否存在。

### 5.6 成本

报告以下几项，并画出"效用 vs 注入 token"的 Pareto 前沿：

- 每个探针的平均注入 token 数；
- 每个 unit 的 LLM 调用数（judge、recognizer、consolidator、investigator）；
- tokens-per-correct；
- 延迟。

`ouroboros.md` §11 的三臂预算设计（A 被动、B 加拉取回路、C 按预算截取原始日志）应当放在这条前沿上比较。

### 5.7 安全

- **投毒：** 参考 MINJA（仅通过查询就能达到约 98% 的注入成功率）。通过对话或 propose 注入伪造"决策"，测量注入成功率和持久时间。
- **机密泄漏：** 在流中植入 API key 等敏感内容，检查它们是否被记忆，以及是否在之后被注入。
- **自指污染：** 答错的内容被记住，下次又被服务（见之前指出的"错误答案被记忆"问题）。

### 机制 → 指标对照（确保每个机制都有敏感指标）

| 机制 | 敏感指标 | 探针 |
|---|---|---|
| V 衰减 / λ | 保留曲线、需求校准 AUROC、L_purge | 8、9 |
| 使用信用 η | 需求校准、曝光 Gini、recognizer P/R | 1、8 |
| shadow credit | 新记忆首次服务时间、starvation 恢复 | 8 |
| C/M/A 三池、cap_m | 缓存归一化得分、驻留时间、抖动 | 8、12 |
| ingest dedup / merge | 错误合并率、churn、stale-in-context | 2、4 |
| tension → judge | 各判决的准确率（synonym / update / contradiction / collision，对照账本）、L_serve | 2、4、5 |
| contested 共同服务 | honest-contested 比例、conflated 比例 | 4、5 |
| salience | 重要稀有类的保留 AUC | 8 |
| archive / revive | 历史追问正确率、revive 精度 | 3、8 |
| τ_sim 抑制、θ 门 | 干扰曲线斜率、context precision | 12 |
| recall_miss 拉取回路 | repair yield 差值、false-repair 率、成本 | 11 |

## 6. 协议

### 6.1 P1 开环回放 + 被动探针（主力，零 API 可跑）

- 事件流灌入引擎。到探针时刻时，先 `snapshot = deepcopy(engine)`，再 `snapshot.retrieve(...)`，然后丢弃快照。
- 或者给 `retrieve` 加一个 `dry_run=True` 参数，让所有副作用走一个 no-op sink。
- 优点是完全排除观察者效应（对应 D5），同一状态可以反复用不同探针测量。

### 6.2 P2 闭环模拟用户（测信用和拉取回路）

- 模拟用户持有账本。按账本和需求过程发问，看到回答后，按真实日志中统计到的"纠错率、追问率"做出反应（给出纠正、表示不满、重复提问）。
- **Sim2Real 风险：**
  - *Mind the Sim2Real Gap*（451 名真人）发现，模拟用户过于配合、风格单一、不会表现挫败；
  - *Lost in Simulation* 发现，换一个模拟 LLM，成功率最多差 9pp，而且困难任务被低估、中等任务被高估。
- **对策：**
  - 用两个模型族做模拟器，只报告两者一致的结论；
  - 按真实日志校准纠错率；
  - 注入不配合的行为（不纠正、纠正错误）。

### 6.3 P3 真实日志（只做开环）

- 历史上的纠正是另一个助手引出的，同一段日志不能用来评测"我的回答引出的反馈"。
- Replay 类离线评估只在记录策略是随机的情况下才无偏（Li et al. 2011）。
- 所以真实日志只用于：P1 式的开环被动探针、生成器参数拟合，以及合成→真实的排名一致性检验。

### 6.4 P4 可执行编码轨

参见 4.5 的轨道 C。它是"记忆 → 行动"的终极检验，也是唯一能回答"记忆是否让 agent 更能干活"的轨道。

### 6.5 P5 对抗

包括投毒、机密植入、自指污染，见 5.7。

### 6.6 基线

| 基线 | 回答的问题 |
|---|---|
| none | 记忆有没有用 |
| full-context（放得下时） | 动力学是否比"全塞进去"更好或更省 |
| raw-log-at-budget（最近 B 个 token 的原始日志） | 结构化是否优于截断 |
| **oracle-ledger 注入**（直接注入账本中的有效事实） | 回答者的天花板。把差距分解成"记忆的锅"和"回答者的锅" |
| append-only（不遗忘、不合并） | 遗忘本身的价值 |
| LRU / LFU / LRFU / ARC | V 动力学是否优于经典缓存策略 |
| HLR 需求预测器 | V 是否优于一个简单的学习型需求模型 |
| 各消融 | 各机制的边际贡献（需通过覆盖率闸门） |

## 7. 统计与效度

### 7.1 功效

基于 qa-cont-v4 实测的方差计算（命令保存在 `dm-run/eval/` 下）：

**连续量表（1–5 分）：**

| 配对差 sd | Δ=0.5 所需 n | Δ=0.3 所需 n |
|---|---|---|
| 1.25（臂间差） | 50 | 137 |
| 0.82（特性集差） | 21 | 59 |

**二值配对（McNemar，α=0.05，功效 0.8）：**

| 不一致率 | Δ=0.10 | Δ=0.05 |
|---|---|---|
| 0.15 | 116 → ×DE 2.9 = **337** | 469 → 1361 |
| 0.25 | 194 → **563** | 783 → 2271 |

- 设计效应 DE = 1 + (m−1)·ICC。取每条流 m=20 个探针、ICC=0.1，得到 DE=2.9。
- 所以同样的探针总数，**分布到更多流上**更划算。建议 ≥ 25–30 条流。

### 7.2 分析规范

- **主分析：**
  - 以流为聚类单位，算配对差和聚类稳健标准误；
  - 或用混合效应模型：`outcome ~ system + (1|stream) + (1|probe_type)`。
- **多重比较：** 13 个消融组内做 Holm 校正。
- **预注册：** 写明主指标（建议：clean-support 与期望效用）、主比较（ours vs decay_only vs flat vs oracle），以及 MDE。
- **流级 dev/test 划分：** 调参（λ、θ、cap_m）只能用 dev 流。现在 T=220、seeds 0–9 既用于调参又用于报告，这属于在测试集上调参。
- **噪声地板：** 同一配置换 seed 重跑，得到的差异分布就是"什么差异算真的"的参照。

### 7.3 效度威胁清单

| 威胁 | 表现 | 缓解 |
|---|---|---|
| 生成器与系统耦合 | 生成器的"显式更新"措辞恰好是系统的抽取模板 | 用不同模型族渲染；加入隐式和推断档；做真实→合成的排名检验 |
| 显式失效的同义反复 | 事件本身写着"作废"，系统照做，谈不上智能 | 报告按显式度分层的结果 |
| 裁判偏宽 | 含糊答案判对 | 裁判压力测试；nugget 判分 |
| 标签噪声 | 账本本身有错（LoCoMo 键 6.4% 有误） | 双人核对，抽样报告一致率 |
| 口径错杀 | 见 D1 | 口径单测：理想输出必须得满分 |
| 机制未触发 | 见 D2 | 覆盖率闸门 |
| 观察者效应 | 见 D5 | 被动探针用快照 |
| 在测试集上调参 | 见 7.2 | 流级划分 |
| 天花板 / 地板 | 见 D3 | 难度维度扫描；报告曲线而不是单点 |

## 8. 落地路线（对应本仓库）

### Phase 0：离线、零 API，1–3 天

1. **修口径。** `sim/world.py` 的 `relevant()` / `valid()` 识别聚合体成员（参考 `dm-run/eval/rescore_aggregate.py`），并加一条口径单测。
2. **只读检索。** `MemoryEngine.retrieve(..., dry_run=False)`：当 dry_run 为真时，跳过 shortlisted++、suppressed_by、tension 新增、shadow pending、revive 和信号入队。另外提供 `engine.snapshot()`。
3. **覆盖率报告。** 在 `metrics.Recorder` 里增加操作计数和 decision-flip 统计；`experiments/run.py` 的输出附上覆盖率表。
4. **账本世界。** 新建 `sim/ledger_world.py`，实现 4.2 的所有事件类型，先用模板渲染，嵌入沿用 SyntheticEmbedder。
5. **精确指标。** 实现 5.2 和 5.3 的全部指标，包括生存分析、保留曲线、需求校准和缓存归一化得分。
6. **缓存基线。** 在 `baselines/` 下实现 LRU、LFU、LRFU、ARC、append-only 和 Belady MIN（需求已知）。

### Phase 1：校准

- 从 L0 日志的提及记录中拟合再提及间隔分布和会话间隔分布，更新生成器参数。
- 用拟合出的环境重新扫描 λ 和 idle，检查现在的默认值是否处在合理区间。

### Phase 2：文本化

- 用 LLM 渲染对话，接入真实嵌入（bge），引入回答层与 nugget 裁判。
- 做裁判压力测试。
- 加入 oracle-ledger 基线。

### Phase 3：闭环

- 实现双模型族的模拟用户，测拉取回路和信用回路。
- 把 §11 的三臂预算实验放到 Pareto 前沿上比较。

### Phase 4：真实

- 对 3–5 条 L0 日志做脱敏，并标注账本。
- 检验合成→真实排名的 Kendall τ（期望 ≥ 0.6，否则要回头修生成器）。

### Phase 5：行动

- 构建可执行编码轨，规模 10–20 个序列，并预注册。

## 9. 开放问题

- **时间用什么度量？** 衰减按 turn 计还是按 wall-clock 计？真实开发存在"隔一周回来"的情况。建议两种时钟都记录，并在评测中分别分析它们对保留率的影响。
- **记忆的价值应该用答案来衡量，还是用行动来衡量？** MemoryArena 和 VibeMemBench 都表明两者可能不一致。
- **"仍然为真但不再需要"被遗忘，算不算错？** 本文用未来需求来判定。但用户偶尔会翻旧账，这时第 3 类探针的权重应该由产品需求来决定。
- **信用回路的偏差。** 如果 recognizer 系统性地偏向某类记忆，V 会自我强化。需要长时程的曝光公平性监测。
