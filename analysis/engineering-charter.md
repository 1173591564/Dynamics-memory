# 复杂系统工程与闭环开发规范章程

> 状态：现行 · 开发过程标准（14 条 + 五维 DoD + 门禁链）。
> 采纳记录与**已声明例外**、计划错误码见 [target-architecture.md](target-architecture.md) §9.2 N46；
> 本文件约束开发行为，不替代系统设计（唯一设计仍是 target-architecture.md）。

*(Engineering Charter & Execution Standards for Complex Systems)*

---

## 序言：核心工程哲学

本章程旨在杜绝**“测试全绿但生产断路”**、**“符号达标但逻辑架空”**与**“形式合规代替功能闭环”**的形式主义工程缺陷。在复杂系统与关键链路开发中，所有开发人员与 Agent 必须无条件遵守以下四大底层哲学：

1. **调用链即生命（Call-Graph Grounding）：** 生产代码中的任何符号，其存在的唯一合法性在于其位于真实运行时的主调用链上。不存在任何“仅供测试调用”的生产符号。
2. **显式失败原则（Fail-Loud & Fail-Fast）：** 严禁任何形式的静默容错、静默降级或无原则默认值。非法配置必须阻断启动，重试耗尽必须进死信，容量超标必须出显式背压。
3. **严格界限分离（Strict Boundary Separation）：** 锁内事务只做确定性内存/数据库状态转移；所有外部 I/O（模型推理、Embedding 向量化、网络通信、文件系统大读写）必须严格置于事务与服务锁之外。
4. **端到端闭环检验（End-to-End Verification）：** 单元自洽不代表系统可用。只有贯穿“请求输入 → 校验/准备 → 锁内提交 → 状态转移 → 回执与观测”全生命周期的验证，才算功能就绪。

## 第一章 架构契约与接线规范 (Architecture & Wiring)

### 第 1 条 【拒绝孤立符号 (Zero-Orphan Rule)】
- 新增或重构任何架构符号（函数、类、枚举、变量）时，**禁止“先实现符号、后写单测、暂不接线”的孤岛模式**。
- **强制约束**：符号的定义（Definition）、主干分发层的接线（Wiring in Dispatch/Worker/Route）以及状态机的消费（Consumption）必须在同一变更中原子提交。

### 第 2 条 【真伪契约一致性 (Functional vs. Formal Compliance)】
- 严禁为了满足 AST 语法分析、代码清单检查或哈希校验而编写“空壳符号”或“伪实现”。
- 架构清单（Inventory）与架构契约（Contract）必须如实反映运行时拓扑。文档与清单是系统运行状态的影子，不是掩盖断路的工具。

### 第 3 条 【包与模块依赖单向收敛】
- 跨层调用必须严格遵循分层边界：
  - `Transport`（HTTP/CLI） → `Service`（编排） → `Dispatch/Core`（算法与状态机） → `Store`（存储与证据）。
- 严禁逆向导入或循环导入；向后兼容 Shim（如旧路径导出）仅允许做无逻辑转发，不得作为生产业务的核心依赖路径。

## 第二章 状态机、事务与存储纪律 (State Machines & Storage)

### 第 4 条 【有界重试与死信收束 (Bounded Retries & Dead-Letter)】
- 任何异步任务、工作流或语义任务的状态机，**必须具备严格且有限的最大重试次数（Finite Max Attempts）与退避算法（Exponential Backoff）**。
- 严禁设置“无限重试（Infinite Requeue）”。重试耗尽必须原子转移至死信状态（`dead` / `dead_letter`），并记录末次失败堆栈，保证失败对运维与监控绝对可见。

### 第 5 条 【数据库事务与连接安全 (SQLite/DB Discipline)】
- 深入理解底层数据库驱动的连接模式（如 Python `sqlite3` 的隐式事务行为）。
- 初始化 DDL、索引创建与版本记录操作（`schema_version`）执行完毕后，**必须显式提交（`commit`）**，严禁残留隐式未决事务导致后续业务事务发生死锁或 `cannot start a transaction within a transaction` 崩溃。
- 版本门控：数据库启动时必须严格校验版本号，**遇到高版本数据库必须抛出致命异常（Fatal）阻断启动**，严禁静默忽略或自动向下抹除。

### 第 6 条 【状态与效果原子性 (Atomic Checkpoint & CAS)】
- 业务效果应用、任务状态流转、版本推进（Revision increment）与去重回执必须在同一个数据库事务内提交。
- 采用 CAS（Compare-And-Swap）机制防止并发实例或脑裂覆盖状态；CAS 冲突必须立即回滚并触发内存状态安全自毁或重载。

## 第三章 算法与数据流严谨性 (Algorithms & Data Integrity)

### 第 7 条 【时间序与容量收口语义 (Time-Series & FIFO Consistency)】
- 在涉及内存池、淘汰策略（LRU/FIFO/LFU）与容量限制的算法中，必须严格推演状态转移。
- **纯函数模拟原则**：容量计划（如 `plan_capacity`）必须是无 I/O 的确定性纯函数。新迁入/新归档条目必须赋予正确的逻辑时间戳（最新进入而非最早淘汰），严禁出现语义颠倒。
- **背压机制**：当容量受限且所有条目均处于保护/锁定状态无法淘汰时，必须向调用方返回显式背压信号（`Rejected("capacity_backpressure")`），严禁静默丢弃或破坏容量上限。

### 第 8 条 【来源校验与因果一致性 (Provenance & Causality)】
- 任何提议或记忆生成，必须严格校验输入凭据（Source Unit IDs）的存在性与因果上界（`before` 限制）。
- 严禁引用“未来日志”或“虚构凭据”；对空引用、越界引用或未接地内容（Ungrounded Content）必须无条件拒绝。

## 第四章 安全、鉴权与配置规范 (Security & Configuration)

### 第 9 条 【默认安全与文件权限 (Secure by Default)】
- 所有在文件系统上生成的凭据文件、Token 文件、进程间通信载荷（如 CLI `--file` 临时文件），**必须在创建时立即施加最小权限控制（POSIX `0600`）**。
- 临时文件必须在 `try...finally` 块中确保执行完毕或异常退出时被可靠销毁（`unlink`），防止敏感数据滞留。

### 第 10 条 【配置解析严禁宽容兜底】
- 系统的运行模式、核心 Pipeline、外部服务端点等关键配置，解析时必须执行白名单匹配。
- 遇到未定义、拼写错误或未知取值，**必须立即抛出异常阻断启动**。严禁将未知非法值静默归纳至“默认模式”，防止运维误配置导致非预期逻辑运行。

### 第 11 条 【权限分立与回执幂等】
- 普通 Agent 访问、主系统查询与人工复核审批（Human Review）必须具备独立的 Capability 鉴权通道。
- 变更接口必须支持请求级唯一 ID 去重（Idempotency），对于重复请求必须返回原回执并标注 `replayed`，对冲突请求必须显式返回 `409 Conflict`。

## 第五章 质量门禁与反思验收流程 (Definition of Done & Gates)

### 第 12 条 【拒绝“局部单测达标”假象】
完成一项开发的判定标准，绝不是“针对该函数写的 3 行单测 PASS”，而是必须满足以下 **五维交付闭环（DoD）**：

| # | 维度 | 要求 |
|---|---|---|
| 1 | 代码与接线 | 符号在主回路（Worker/Route/Service）中被真实调用 |
| 2 | 错误与边界 | 覆盖非法输入、并发竞争、事务冲突、超时重试耗尽等失败态 |
| 3 | 架构与契约 | 通过架构契约检查，无孤立符号，无非法依赖，无哈希漂移 |
| 4 | 端到端贯通 | 从协议入口（HTTP/CLI）到持久化存储全链路数据正确落盘 |
| 5 | 观测与可维 | 状态字段暴露于健康检查（/health /signals），指标真实反映 |

### 第 13 条 【每一次提交前的强制门禁核检】
在宣布任何阶段性收工或提交代码前，必须无条件执行并全绿通过以下门禁指令链：

1. **全量测试套件（严禁跳过/过滤）：**
   ```bash
   python -m pytest tests/ -q -p no:cacheprovider
   ```
2. **架构契约与全量符号检查：**
   ```bash
   python analysis/check_architecture.py
   ```
3. **全局验收综合核检（包含性能、数据流、元评测全集）：**
   ```bash
   python analysis/acceptance_check.py --full
   ```
4. **跨语言/客户端网桥协议测试：**
   ```bash
   bun test tests/memory_bridge.test.ts
   ```

> 执行边界（N46）：完整 Bun 超时用例与 bench smoke 目前仍属未验证项，按“如实记录，不得过滤”执行；
> 门禁只规定“提交前必须跑什么”，不授权 AI 自行宣布“完成/可验收”——该判断属于人。

## 结语：开发者的誓词

> “我不以测试表面的绿色欺骗自己，我不以静态的符号清单应付架构；
> 我敬畏每一行代码在生产运行时可能遭遇的异常、并发与崩溃；
> 我交付的每一处变更，必须具备坚固的调用链、明确的边界约束与完整的端到端闭环。”
