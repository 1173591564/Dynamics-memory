# 第 1 批计划：L0 提交后的逐单元恢复

## 已核实的边界（基于 main 642caa6）

`MemoryService.observe` 在 `log.sqlite` 事务中 `append_unit`，随后锁外运行 candgen，最后在服务锁内通过 `engine.report_unit` 将调查任务单独提交到 `tasks.sqlite`，应用候选和 step；正常退出的 `/save` 不是每轮事务的一部分。任何一步崩溃都可能留下只存在于 L0 的单元，重启只对齐游标，不补处理。`tasks.sqlite` 的调查效果/回执 checkpoint 已支持同库事务。语义任务仍是内存队列，不属于本批。

## 本批目标 / 非目标

目标：新在线 L0 单元与待办记录原子提交；按原 id、t、scene、原文及当时实体首次出现情况恢复；候选结果可复用；引擎效果、调查任务交接和逐单元回执在 `tasks.sqlite` 一个事务里提交；跨库确认以回执为准，恢复不会重复应用。错误、积压可观察，自动恢复有界。

非目标：不回放升级前没有待办的全部旧日志；不使旧 `/observe` 重试具备 request-id 去重；不解决其他 API 或语义任务的持久化；不声称多 sidecar 实例共享引擎安全、模型 exactly-once 或远程 L3 验证。保留既有服务 API；`/signals` 增加逐单元 backlog 指标。

## 格式、顺序、故障协议

* `log.sqlite` 新增 `unit_work`，仅**新在线追加**的单元在原 L0 写事务里插入 pending 行；旧库 schema 增量创建，不自动为已有 units 建待办。结果（包括合法空候选或 candgen 失败标志）、错误/重试时间和确认状态仍在此表。`add_unit(id, ...)` 的显式历史导入不生成工作。
* `tasks.sqlite` 新增 `unit_receipts(unit_id PRIMARY KEY, response)`；在同一个 `BEGIN IMMEDIATE` 事务里：校验 checkpoint revision、执行单元的引擎效果、入队调查信号、写入新 checkpoint、写回执。任何入队容量/SQL/业务错误都回滚整个事务并恢复进程内对象；不把回执与效果拆为两次提交。语义信号仍按现有易失语义在效果提交之后发出，故其崩溃恢复归第 2 批。
* `log.sqlite` 的 done 确认只能在 `tasks.sqlite` 回执可见后写入。若任务库已提交但日志确认前退出，重启读回执并确认，不再执行效果/重复交接；若任务库未提交，日志仍 pending 并重试原单元。确认失败仍保留待办；若任务库提交结果不确定，服务进入 checkpoint fault，必须重启，不能继续用回滚内存覆盖数据库。
* 同一服务中同一 unit 一次只允许一个处理者；处理器按 L0 id 顺序领取，模型调用在服务锁外、效果在锁内；并发 `/observe` 可先返回已登记待办，不能越过仍未处理的旧单元提交效果。多 sidecar 共享同一内存引擎不在支持范围，checkpoint revision CAS 拒绝落后的实例。独立于调查员开关的后台恢复器按周期扫描最早的 eligible 新待办，错误有持久化退避；不遍历旧日志生成模型调用。结果先持久保存，再尝试效果，避免容量不足/效果失败时反复请求模型。启动恢复不依赖 `/save` 或正常关机。
* 调查信号的 `on_emit` 在单元提交期间改为收集器：保留原引擎的 `report_miss/report_unit` 逻辑及合并规则，待任务库同一事务入队；其他语义信号仍走既有内存队列。事务失败时必须连同引擎对象及语义队列原位回滚，不能留下已回滚效果的信号。后续普通 `/miss` 和独立调查任务仍走旧通道。
* 在线 append 时记录上一轮问题及当时已召回内容的最小上下文；若旧库无此记录，按 L0 `t` 之前的前驱用户单元恢复问题，不伪造已召回结果。单元所带 `scene`、逻辑时间与首次实体按原 L0 取；场景更新按已处理的单元时间排序，不能让较早模型完成覆盖较新的场景。
* 来源使用旧 L0 id 和 t；`new_entities` 按当时 t 之前的日志计算；上一轮用户文本从 L0 的前驱单元获取。前一轮非持久检索的引用如重启后不可用则不伪造。处理较旧单元不得把较新 scene 或逻辑时钟倒退。

## 可执行验收

1. 进程在 L0 提交后、抽取前强制退出：新连接看到原始单元和 pending 行，启动后恢复同 id/t，无第二次 append。
2. 抽取结果保存后、效果提交前强制退出：恢复复用结果；空候选也完成，不循环调用模型。
3. 在任务/效果/checkpoint/回执提交后、L0 done 前强制退出：重启只确认、不重复记忆来源/证据或调查入队。
4. 任务容量满、调查入队 SQL 失败、checkpoint 冲突/写回执失败：待办保留，效果未提交或服务拒绝继续写；队列恢复后可以重试。
5. 重复和并发消费同一单元：至多一份效果/调查交接；升级前旧 L0 不自动重放。
6. candgen 失败仍持久交给 extract_due；成功但合法空结果正常 done；`/signals` 显示待处理、已缓存结果、失败/退避数量。
7. Python 全套、TIDE、静态检查及子进程 `os._exit` 注入通过；明确假模型与真实网络模型验证的区别。

上线前应停止服务并备份整个状态目录（两个 SQLite + WAL + 快照）；升级后 `tasks.sqlite` checkpoint / 回执和 `log.sqlite` work 必须作为一组恢复，不能只回滚一个数据库。旧版本不认识逐单元回执，不能安全地直接降级并继续写入。不要将此批当作 request-id 可靠重传或语义任务持久化完成。

## 实施后的核对与边界（本批）

- 原 `observe` 中的「append 后先发调查任务／锁外抽取／锁内直接写池」已由逐单元待办消费取代，调查信号仍通过原 `engine.report_miss/report_unit` 组装，不维护第二套独立任务格式。`TaskStore._enqueue` 是原 `enqueue` 的同事务实现，不再嵌套 `BEGIN`。普通 `/miss`、已有调查任务/操作回执及语义 worker 不改协议。
- 后台单元恢复器在 CLI 启动（包括 `--no-agent`）时独立启动；Python 服务对象可显式 `start_unit_recovery()` 或 `process_pending_units()`。在线请求通常同步返回原候选数；若已有单元在执行或退避，返回 `{pending:true}`，L0 与 pending 已被接受。队列容量不足在应用时给 503，但 **L0 已接受**，恢复器继续重试；客户端不能把 503 理解成可以无副作用重投 `/observe`。
- 抽取结果（含合法 `[]` 或失败标记）写在 L0 的工作行，随后效果/调查任务/checkpoint/回执在任务库原子提交，最后单独将日志行置 done。回执存在时重启只做确认，即使后来 `/save` 已推进 checkpoint revision，也不重复效果；提交结果不确定时服务故障关闭直到重启。
- 业务事务失败恢复现有 Memory 对象、服务计数、游标及语义信号队列；未提交的语义信号不漏到后台消费者。已提交后尚未执行的语义 worker 信号仍是**易失的**，不借本批声称其可靠恢复。
- 旧 `log.sqlite` 增量建表，不为历史日志产生待办；旧 `state.pkl` 在还没有 SQLite checkpoint 时照旧加载。首个单元效果提交后，`tasks.sqlite` checkpoint 成为权威；旧快照损坏时不能覆盖它，checkpoint 损坏或有单元回执却缺 checkpoint 时拒绝启动。
- 有故障的最早单元会在可观察的持久退避状态中阻止后续单元越序提交；不会自动标记完成或丢弃，但持续故障需要修复外部依赖／容量，积压会增长。每单元效果需序列化整个 checkpoint、在任务库写事务内执行嵌入，优先保障正确性而非吞吐。
- 原始 L0 单元可能含敏感文本；本批不改变原文持久化／日志工具脱敏边界。跨库不是单个分布式事务，恢复正确性以同一状态目录的**配套**数据库与备份为前提；没有 HTTP 请求 ID 去重，也没有模型恰好调用一次承诺。不同项目/多个 sidecar 同时写同一引擎不受支持；CAS 用于拒绝旧实例，而非提供多主一致性。
