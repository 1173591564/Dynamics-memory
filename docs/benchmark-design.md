# TIDE：面向"动力学记忆"的评测框架设计

**TIDE** = **T**emporal **I**ntegrity & **D**emand-aware **E**valuation，即"时间完整性与需求感知评测"。

> **定位：** 这是一个与具体系统无关的基准设计，任何带状态、会遗忘、会自我修订的 agent 记忆都可以用它来评：Mem0、Zep/Graphiti、Letta/MemGPT、A-Mem、Dynamics-memory 等。
> **目标：** 在构念定义、可验证性、元评测三个方面经得起审稿人和同行质疑。

---

## 0. 核心主张

现有的记忆基准（LoCoMo、LongMemEval、MemoryAgentBench、HaluMem、Memora、MemoryArena、BEAM……）评测的其实都是一个隐含问题：**"信息被存下来了没有"。**

而动力学记忆要回答的是另一个问题：

> **在有限预算下，系统能否在每一个需要的时刻，提供"此刻有效且有用"的知识，并且不提供此刻已经无效或有害的知识。**

TIDE 围绕这个问题做了五个设计决定：

1. **构念形式化。** 把"记忆能力"定义为：相对于一个"全知且受同样预算约束的 oracle"，在一条时间流上累计的服务效用，也就是一种 regret 视角。这样遗忘、更新、囤积都会被自然定价，不需要额外打补丁。
2. **两类金标准。**
   - **世界账本：** 每条事实都有有效期、作用域和依赖关系，回答"什么在此刻为真"。
   - **需求过程：** 什么时候、以多大权重需要什么，回答"什么值得留"。

   账本和需求过程都先于文本生成，文本由它们渲染出来。
3. **用曲线代替分数。** 每种能力都配一个可调的"应力旋钮"，例如时间间隔、更新次数、干扰数量、级联深度、显式程度。系统在旋钮上的退化曲线才是能力画像；单点分数只是曲线上的一个样本。
4. **可验证性优先。** 能用精确匹配或可执行测试判分的，就不用 LLM 裁判。必须用裁判的部分，要先通过人工一致性测试和植入错误的压力测试。
5. **基准本身要被验证。** 按 Bean et al.（NeurIPS 2025）对 445 个 LLM 基准的系统综述给出的构念效度建议，以及 BetterBench 的 46 条质量标准，TIDE 在发布前需要完成：
   - 已知组检验；
   - "干预 × 能力"特异性矩阵；
   - 剂量–反应检验；
   - 概化理论信度分析；
   - IRT 题目筛选；
   - 与生态真实任务的收敛效度。

## 1. 构念定义（形式化）

### 1.1 对象

- **世界** W 包含一组事实 f，每条事实有：
  - 值 `v_f`；
  - 有效区间 `[s_f, e_f)`（双时态：事件时间和记录时间）；
  - 作用域 `σ_f`；
  - 类型 `kind_f`：decision / preference / status / method / constraint / transient；
  - 重要度 `w_f`；
  - 依赖 `dep_f ⊆ F`：上游事实变化时，下游事实失效。
- **观察流** `o_1 … o_T`：每个观察带 turn 索引 t 和墙钟时间 τ，按会话分组，会话之间有间隔。
- **需求事件** `n = (t_n, q_n, G_n, H_n, w_n)`，分别是：
  - 时刻；
  - 查询；
  - 金事实集 `G_n`：此刻有效、且回答所必需的事实；
  - 有害集 `H_n`：与查询相关、但此刻已经无效的事实，包括被取代的、被撤回的、过期的临时状态、作用域不匹配的、上游已失效的派生值；
  - 权重 `w_n`。
- **被测系统** M 只需实现三个接口：
  - `ingest(o_t, t, τ)`；
  - `serve(q, t, τ, B) → c`，其中上下文 c 的长度不超过 B 个 token；
  - `feedback(signal)`：可选，只在闭环赛道开放。
- **读者** R：一个固定的 LLM，由 harness 统一提供，给出回答 `a = R(q, c)`。

### 1.2 效用与头条分数

对每个需求事件，分别计算检索层和回答层的效用：

```
检索层   u_ret(n) = w_n · [ S(c, G_n) − λ_H · 1{c ∩ H_n ≠ ∅} ]
         S: 上下文对金 nugget 的支持比例；λ_H 是有害注入的惩罚权重

回答层   u_ans(n) = w_n · U[k(a)]
         k(a) ∈ {current, current+history, honest-contested, abstain-ok,
                 abstain-bad, stale, conflated, fabricated}
```

对全部需求事件聚合后取归一化，得到**归一化时间效用（NTU）**：

```
U(M, B)   = Σ_n u(n) / Σ_n w_n
NTU(M, B) = ( U(M,B) − U(none) ) / ( U(Oracle_B, B) − U(none) )
```

- `Oracle_B` 是全知 oracle：在每个需求时刻，把 `G_n` 用最简形式注入，并受同样的预算 B 约束。它就是读者的天花板。
- `none` 表示不用记忆。
- 头条分数取 NTU@B*（B* = 2k tokens），同时报告 NTU 在 B ∈ {512, 2k, 8k} 上的曲线。

**为什么这样定义：**

- **囤积不占便宜。** 预算有限，而且有害注入会被扣分。
- **正确遗忘自动获益。** 把已经失效的内容腾出来，能换来预算和"无害"两方面的收益。
- **有上下界、可归一化。** 不同读者和不同难度下的分数可以放在一起比较。
- **与系统无关。** 只依赖三个接口，内部实现是黑箱。
- **有文献依据。** 需求加权的思路来自 Anderson & Schooler（1991）：记忆是对环境需求概率的适应，这类需求概率对新近度和频率都呈幂律。Oracle 归一化的思路来自缓存领域的 Belady MIN（离线最优淘汰）。

### 1.3 效用表（默认值，需做敏感性分析）

| k(a) | U | 说明 |
|---|---|---|
| current / current+history / honest-contested / abstain-ok | +1 | 正确行为 |
| abstain-bad | 0 | 保守但没帮上忙 |
| conflated | −1 | 新旧混杂，或作用域张冠李戴 |
| stale | −1.5 | 自信地给出过期的值 |
| fabricated | −1.5 | 编造 |

发布时附上 stale 和 fabricated 惩罚权重在 {0, 0.5, 1, 1.5, 3} 上的系统排名稳定性（Kendall τ）。如果排名对权重敏感，就必须在报告里说明。

## 2. 能力分解：八个维度、八条应力曲线

每个维度都有：操作性定义、一个应力旋钮 x、一条曲线 `U_a(x)`，以及一个摘要值。摘要值取曲线在 log x 上的归一化 AUC，或者一个可以直接解释的"半衰期"。

| 维度 | 操作性定义 | 应力旋钮 x | 摘要指标 |
|---|---|---|---|
| **A 获取** | 从对话中形成正确的记忆 | 显式度（明说 / 隐含 / 需推断）；信息埋藏深度 | 各档的准确率 |
| **R 保持** | 间隔 Δ 之后，仍能服务有效事实 | Δ ∈ {1, 4, 16, 64, 256, 1024} turn，另加墙钟间隔 {1h, 1d, 1w, 1mo}；按重要度分层 | **有效记忆半衰期** Δ½（U 降到 Δ=1 时一半的间隔），按重要度分层报告 |
| **V 修订** | 更新后服务新值、停止服务旧值 | 更新次数 k ∈ {1, 2, 4, 8, 16}；隐式 vs 显式；部分字段更新；回滚 A→B→A | k 曲线的 AUC（参考 PI-LLM）；**切换延迟** L_serve、**清除延迟** L_purge（Kaplan–Meier 中位数） |
| **P 传播** | 上游变化后，下游派生知识随之失效或更新 | 依赖深度 d ∈ {1, 2, 3}（参考 RippleEdits / MQuAKE） | 按深度的准确率；下游陈旧率 |
| **C 冲突与作用域** | 同一实体在不同作用域下取不同值，以及用户自己也没定下来的情况 | 作用域数量；未决 vs 已决 | honest-contested 率、conflated 率 |
| **F 卫生（该忘的忘）** | 不服务已撤回、已过期、临时性的内容；该弃答时弃答 | 撤回显式度；临时状态寿命 | 有害注入率、Absence 准确率（参考 MEME 的 Absence 类）、选择性风险曲线 |
| **I 抗干扰** | 在相似且无关的记忆中精确命中 | 干扰数 m ∈ {0, 4, 16, 64, 256} | 干扰曲线的斜率 |
| **Rc 恢复**（闭环赛道） | 失败并得到反馈后，下一次能否答对 | 反馈类型（显式纠正 / 隐式不满 / 无反馈）；再问间隔 | repair gain = U(开环) 与 U(闭环) 在重复需求上的差值；每次修复的成本；错误修复率 |

此外还有两个横切维度：

- **效率 E：** 注入的 token 数、每个 turn 的离线 LLM 调用数、服务延迟，最终落到 NTU–成本的 Pareto 前沿上。
- **鲁棒性 S：** 投毒（参考 MINJA，仅通过查询就能达到约 98% 的注入成功率）、机密泄漏、同义改写后的一致性。

**为什么要用曲线：**

- PI-LLM 发现，准确率随更新次数呈对数线性下降。这种规律只有在旋钮上连续扫描才看得见，单点测试会同时掉进天花板和地板。
- 曲线还能直接回答工程问题，例如"这个系统的记忆半衰期是 60 turn 还是 600 turn"、"更新 8 次后还剩多少"。这比"LoCoMo 72.3 分"更有信息量，也更难刷分。

## 3. 三层架构：控制与生态效度之间的三角验证

| 层 | 名称 | 内容 | 金标准 | 判分方式 | 主要作用 |
|---|---|---|---|---|---|
| **L1** | 受控程序化层 | 由账本和模板生成的短流；值是唯一的伪词 token | 精确 | 字符串匹配、多选 | 画出八条应力曲线；因果隔离 |
| **L2** | 情境层 | 同样由账本驱动，但用多模型族的 LLM 渲染成真实的开发者对话，长 200–1000 turn、多会话 | 精确（账本），经过渲染验证 | nugget + 经验证的裁判；多选作辅助 | 头条 NTU；各能力画像 |
| **L3** | 生态层 | (a) 真实开发日志：脱敏，人工标注需求事件与账本；(b) 可执行编码序列：fixture 仓库，决策埋在历史会话里，用隐藏测试判分 | 人工标注 / 可执行 | 人工 + 测试 | 收敛效度；回答"对真实工作有没有用" |

**分层的逻辑：**

- L1 保证能测清楚。
- L2 保证测得像。
- L3 保证测得有意义。
- 基准的权威性来自层间一致：L1/L2 的系统排名必须与 L3 显著相关（见 8.4），否则 L1/L2 就是在测别的东西。

**L3(b) 的设计要点：**

- 借鉴 DreamBench-SWE 的三会话陷阱：每个任务第一会话埋决策，第二会话改决策，第三会话执行，隐藏测试只在遵守最新决策时通过。
- 使用 CSPRNG 生成的 token，防止模型凭先验猜中。
- 事先预注册。
- 预期到零结果的可能：VibeMemBench 中 12 个"记忆 × 求解器"组合里有 11 个不优于关闭记忆。零结果本身就是有价值的发现。

## 4. 赛道与协议

### 4.1 三条赛道

| 赛道 | 读者 | 反馈 | 回答的问题 |
|---|---|---|---|
| **T1 固定读者**（主赛道） | harness 统一提供 | 无 | 记忆系统本身好不好（排除读者差异） |
| **T2 端到端** | 系统自带 | 无 | 整体产品好不好 |
| **T3 闭环** | 固定 | 模拟用户实时给出反馈 | 系统能否从交互中自我修复（Rc 维度） |

另设一个可选的白盒附加报告，只面向暴露内部状态的系统。它报告内部分值对未来需求的校准（AUROC、可靠性图）、池驻留时间分布、曝光基尼系数等。**白盒报告不进入排名**，以保证公平。

### 4.2 预算分档

- 所有比较都在同一预算 B 下进行，档位为 512 / 2k / 8k token。
- 每档额外报告"离线计算成本"，即 ingest 阶段的 LLM 调用数和 token 数。一个系统可能只是把成本从服务阶段挪到了摄入阶段，所以两者都要看。

### 4.3 时钟

- harness 同时提供 turn 索引和墙钟时间，并在会话之间插入真实分布的间隔。
- 系统可以选择使用哪种时钟。
- 保持维度 R 分开报告两种时钟下的半衰期。

### 4.4 探针的被动性

- 在 T1 和 T2 中，探针只是**测量**，不应改变系统状态。
- harness 要求系统提供快照和回滚，或者一个只读的 `serve`。不支持的系统，改为对每个探针重放一次流：代价高，但结果干净。
- 在 T3 中，探针本身就是交互负载的一部分，这是闭环赛道的定义。

### 4.5 闭环模拟用户（T3）

- 模拟用户持有账本，按需求过程发问。答错后，按照从真实日志统计出的纠正率和追问率做出反应。
- **已知风险：**
  - *Mind the Sim2Real Gap*（451 名真人）发现，模拟用户过度配合、风格单一、没有挫败感；
  - *Lost in Simulation* 发现，换一个模拟 LLM，τ-bench 的成功率最多相差 9pp。
- **对策：**
  - 用 ≥2 个模型族做模拟器，只报告两者一致的结论；
  - 纠正率参数从真实日志校准；
  - 注入"不纠正"和"纠正错了"两类不配合行为。

### 4.6 平台架构：与被测系统完全解耦

```
┌──────────── TIDE 平台（独立仓库） ────────────┐        ┌──── 被测系统（黑箱） ────┐
│ 生成器 → 账本/流/探针（被测方永远看不到）       │        │                         │
│ Runner：时钟、回放、快照调度                     │  HTTP  │  Dynamics-memory sidecar │
│ Reader：固定读者 LLM                             │ ─────▶ │  / Mem0 / Zep / Letta …  │
│ Scorer：账本裁决 + 闭集映射 + nugget             │ ◀───── │  （各自一个薄适配器）     │
│ Reports：曲线、NTU、CI、元评测                   │        │                         │
└──────────────────────────────────────────────┘        └─────────────────────────┘
```

**解耦铁律**

- 平台不 import 被测系统的任何代码，被测系统也不 import 平台的任何代码。两者只通过协议通信。
- 账本、需求权重、有害集等**真值信息永远不越过协议边界**。被测系统只能看到对话文本和时间戳。
- 由平台持有时钟：时间通过请求参数传给被测系统，被测系统不能自己计时，否则回放不可复现。
- 读者 LLM 和裁判 LLM 都在平台一侧，被测系统只负责返回上下文。T2 端到端赛道例外：此时被测系统返回的是回答。

**协议**：HTTP/JSON，同时提供一个 Python 版本的同构接口，方便本地调试。

| 端点 | 必需 | 说明 |
|---|---|---|
| `POST /reset {stream_id}` | ✓ | 每条流开始前清空状态 |
| `POST /ingest {turn:{user, assistant}, t, ts}` | ✓ | 喂入一轮对话，时间由平台给出 |
| `POST /serve {query, t, ts, budget_tokens}` | ✓ | 返回 `{context: str, meta?}`，context 长度不得超过预算；超出部分由平台截断并记违规 |
| `POST /snapshot` → `{id}`，`POST /restore {id}` | 推荐 | 用于被动探针；不支持的系统，由平台自动退化为"每个探针重放一次流" |
| `POST /tick {t, ts}` | 可选 | 空闲时间推进，用于触发离线维护（衰减、归档、judge） |
| `POST /feedback {query, answer, signal}` | 仅 T3 | 闭环赛道中模拟用户的反馈 |
| `GET /introspect` | 可选 | 白盒报告：内部分值、池状态；不参与排名 |
| `GET /cost` | ✓ | 累计的 LLM 调用数和 token 数，用于成本前沿 |

**适配器**：每个系统一个薄适配器（目标是 100 行以内），负责把上述协议翻译成该系统的原生 API。适配器与平台分开放置，由各系统的作者维护。

**Dynamics-memory 的实际适配（已落地，v0.1）**：引擎侧只加了一项，其余全在平台侧的适配器里完成。

- 引擎：`/recall`、`/search` 支持 `budget_tokens`（按 `approx_tokens` 整行截断，返回实际 `tokens`）和 `passive`（在引擎副本上检索，不改任何状态），对应协议里的 `serve(budget, passive)`。
- 适配器（TIDE 仓库 `tide/adapters/dynamics_memory.py`，约 100 行）：每条流拉起一个全新的 sidecar 进程（临时项目目录、`--port 0`、`--no-agent`），`reset` 就是换进程，`ingest` 对应 `POST /observe`，`serve` 对应 `POST /search {passive: true}`。
- 时钟：sidecar 每次 `/observe` 自增 `_t`，平台逐轮回放，两者天然对齐，所以不需要外部传 `t`。以后如果要评测空闲时间推进（`/tick`）再补。
- 旧的内置 sim（把 `world` 当 `MemorySemantics` 直接喂给引擎）已整体删除。

## 5. 数据生成：先有世界，再有文本

```
┌──────────┐   ┌───────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ 世界采样   │ → │ 事件调度    │ → │ 渲染      │ → │ 验证      │ → │ 探针编译   │
│ 账本+依赖  │   │ 需求过程    │   │ 多模型族   │   │ 可解性    │   │ 多格式答案 │
└──────────┘   └───────────┘   └──────────┘   └──────────┘   └──────────┘
```

### 5.1 世界采样

- 领域：以软件开发助手为主（技术栈、架构决策、约定、环境、任务状态、人员分工），并以个人助理作为迁移领域。
- 每条流是一个项目：包含 50–300 条事实，依赖图是一个 DAG，各类型事实的比例从真实日志估计。

### 5.2 事件调度（需求过程）

- **提及和需求的时间分布用幂律**：真实的再提及间隔服从截断幂律或对数正态，**不要用泊松分布**。参数从真实开发日志拟合，并报告拟合优度（与指数分布做 Vuong 检验）。
- **更新、撤回、作用域分叉、临时状态、干扰事实**，按各应力旋钮的网格注入（L1），或按拟合出的真实比例注入（L2）。
- **会话间隔**从真实墙钟数据拟合。连续性需求（"接着上次的来"）放在长间隔之后的会话开头。

### 5.3 渲染

- 每条流由两个不同的 LLM 家族分别渲染，得到两个平行版本，用于估计"渲染器方差"（见 8.5）。
- 渲染模型不能与任何被测系统内部使用的模型相同，否则会有同源偏差。
- 每个事件标注显式度：明说、隐含、需推断。这样能把"系统没抽到"和"数据太隐晦"区分开。

### 5.4 验证（决定数据质量的关键环节）

1. **全上下文可解性。** 把整条流塞给一个强模型，要求它能答对。不能答对的需求事件剔除，从而保证失败归因于记忆，而不是题目本身不可解。LongMemEval 的 oracle 设置用的是同样的思路。
2. **账本回推。** 由另一个模型只看渲染后的文本回推账本事件，与原账本比对。回推不一致的事件，重新渲染或剔除。
3. **人工抽检。** 按分层抽样抽取 ≥10% 的事件，双人标注，报告一致率。发布标准是 κ ≥ 0.8。LoCoMo 的审计发现约 6.4% 的答案键有误，这个问题必须在发布前解决。

### 5.5 探针编译（可验证性优先）

| 格式 | 用在 | 判分方式 |
|---|---|---|
| 精确值（伪词 token） | L1 全部 | 字符串匹配；检索层直接在 c 中匹配现值和旧值的 token，完全不需要 LLM |
| 多选，带结构化干扰项：旧值、作用域兄弟值、看似合理的编造值、"已作废/不知道"选项 | L1、L2 | 精确匹配；答错时，所选干扰项的类型直接映射到结果类别 |
| 开放回答 | L2 的一部分 | 人工 nugget + LLM 判定（AutoNuggetizer 在 TREC 2024 RAG 中发现这是性价比最好的组合） |
| 可执行 | L3(b) | 隐藏测试 |

L1 中所有事实值都用唯一 token，这是整个设计的关键技巧：服务出的上下文里是否含有旧值、现值或派生值，可以对任何黑箱系统做精确判定，漏斗归因也因此不依赖系统内部。

### 5.6 判分权威：由账本裁决，LLM 只做受限映射

**原则：** 什么是对的，由账本决定；LLM 至多负责判断"这句话表达的是哪个候选"。

#### 候选集闭合

每个需求事件都由账本自动生成一个封闭的候选集：

- 现值；
- 各个历史旧值；
- 作用域兄弟值；
- 上游已失效的派生值；
- "已作废/不存在"；
- "未决（A 或 B）"；
- OTHER。

每个候选预先映射到一个结果类别：现值 → current，旧值 → stale，作用域兄弟值 → conflated，OTHER → fabricated，……

#### 三级映射

读者自由作答后，判分按以下三级依次进行：

1. **字符串或别名匹配。** 值都是唯一 token 或带有指纹细节（版本号、端口、专有名），大多数回答在这一步就能判定。
2. **LLM 闭集分类。** 剩下的回答交给 LLM，只允许它在候选集中选一项，并要求它给出原文依据片段。这是分类任务，不是打分任务。
3. **人工复核。** 两个不同模型族的分类器意见不一致，或者判为 OTHER 的回答，送人工复核。

#### 为什么不直接用多选题

直接给出选项会带来"再认提示"效应：把旧值列出来，本身就可能提醒读者它已经过时。所以只在 L1 的一部分题中用多选，作为对照组来测量这种提示效应的大小。

#### 开放综合题

包括历史追问（"为什么换掉"）和连续性问题（"接着上次的来"）。

- nugget 由账本确定性导出：变更事件、原因、当前进行中的事项。不由 LLM 生成。
- LLM 只对每个 nugget 做二值判定：支持或不支持。
- 裁判须通过 8.7 的验证，并且作为一个"面"计入 G-theory 的方差分解。

#### L3 真实日志

- 真值来自人工标注。
- 另一个来源是日志自身的后验证据：用户后续的确认、提交记录、实际执行的命令。
- 可执行序列由隐藏测试判分。

#### 监控项

| 监控项 | 含义 | 阈值 |
|---|---|---|
| OTHER 率 | 过高说明候选集不完整，或者系统给出了"对但没预料到"的表达 | 超过 5% 须抽检 |
| 两个裁判模型的分歧率 | 衡量 LLM 分类步骤的可靠性 | 公开报告 |
| 人工复核的翻转率 | 衡量 LLM 分类步骤的可靠性 | 公开报告 |

#### 各层判分的构成（目标）

| 层 | 确定性判分 | LLM 闭集分类 | nugget 判定 | 人工 / 测试 |
|---|---|---|---|---|
| L1 | 100%（检索层和回答层） | 0 | 0 | 抽检 |
| L2 检索层 | 100% | 0 | 0 | – |
| L2 回答层 | 约 60% | 约 25% | 约 15% | 复核分歧样本 |
| L3 | 部分 | 部分 | 部分 | 主体 |

### 5.7 规模建议（v1）

| 层 | 规模 |
|---|---|
| L1 | 8 个维度 × 5–6 个旋钮档位 × 30 条流 × 每条流约 10 个需求，共约 1.3 万个需求事件（短流，跑得便宜） |
| L2 | 60 条流 × 300–800 turn × 20–30 个需求，共约 1500 个需求事件；按 30/30 拆分为公开 dev 和隐藏 test |
| L3 | 真实日志 5 条（约 200 个需求事件），可执行序列 20 个 |

规模依据见第 9 节的功效分析：流数量比每条流的题数更重要。

## 6. 诊断层（不进排名，用于解释分数）

### 6.1 黑箱漏斗

L1/L2 用 token 匹配即可完成，对每个失败的需求事件做归因：

```
说过 ─▶ 被 ingest ─▶ 在需要时仍可被服务（存活）─▶ 进入上下文 ─▶ 被正确使用
```

- "存活"段可以通过在需求时刻用 oracle 查询（直接用金事实的原文去问）来探测。
- 按失败发生的阶段给系统出一张损失分解表。这是把 LongMemEval 的 indexing / retrieval / reading 三阶段、HaluMem 的"抽取 / 更新 / 问答"操作级评测，扩展到"存活"这一段，也就是动力学记忆独有的损失。

### 6.2 读者差距

`Gap_reader = U(Oracle_B) − U_max(R)`，其中 `U_max(R)` 是同一个读者在完美上下文下的表现。报告这个量，可以防止把读者的错误算到记忆头上。

### 6.3 更新时间线

对 V 维度的每一次更新，画出"旧值被服务的概率"和"新值被服务的概率"随时间变化的两条曲线，即切换曲线。

## 8. 元评测：如何证明 TIDE 测到了它声称测的东西

这一节决定基准有没有权威性。Bean et al. 发现，只有约一半的基准论证过自己为何是重要现象的有效度量，只有 16% 做过任何统计检验。TIDE 在 v1 发布前要完成以下检验。

### 8.1 内容效度：探针分布代表真实需求

- 从真实开发日志中随机抽取 ≥300 个"用户依赖过去信息的时刻"，人工分类到 8 个维度和各个旋钮档位，得到真实的需求分布。
- L2 按这个分布做分层抽样，头条 NTU 按真实分布加权。
- 同时公开未加权的分维度得分，避免"题目分布由出题人拍脑袋决定"。

### 8.2 已知组效度

对健全性系统，事先写下预测排序，然后检验基准是否复现这些排序。例如：

- S-hoard 在 R 维度高，在 F 和 I 维度低；
- S-amnesic 在 R 维度（Δ 较大时）很低，在 V 维度正常。

排序复现不了，说明对应维度的题目有问题。

### 8.3 特异性："干预 × 能力"矩阵

在一个参考系统上施加受控缺陷，然后测八个维度各自的下降量：

- 关闭更新处理；
- 关闭作用域；
- 加倍衰减速率；
- 关闭干扰抑制；
- ……

**期望得到的矩阵是近似对角的**：关掉更新处理，应该只让 V、P 维度下降，R 维度不应受影响。非对角元过大，说明维度之间有混淆，需要重新设计题目。**这是当前记忆基准普遍缺少的检验，也是 TIDE 最能体现权威性的地方。**

### 8.4 收敛效度与剂量–反应

- **收敛效度：** 在 ≥10 个系统（主流系统、消融变体、健全性系统）上，计算 L2 的 NTU 与 L3 的人工效用评分、可执行成功率之间的 Spearman ρ。期望 ρ ≥ 0.6。同时报告 L1 → L2 → L3 的排名一致性。
- **剂量–反应：** 对参考系统施加强度递增的缺陷，比如丢弃 0% / 10% / 30% / 60% 的更新。对应维度的得分必须单调下降，否则说明该维度不敏感。
- **区分效度：** NTU 不应被"通用检索能力"完全解释。控制系统在标准检索集上的得分后，偏相关仍需显著。否则 TIDE 只是换了壳的检索基准。

### 8.5 信度：概化理论

用 G-theory 做方差分解，考虑以下几个"面"（facet）：系统、流、渲染器、随机种子、裁判。

- 报告 G 系数 `σ²_sys / (σ²_sys + σ²_δ)`，要求 ≥ 0.8。
- 给出达到这一信度所需的流数量和渲染器数量（D-study）。
- 如果渲染器方差很大，说明结论依赖于具体用哪个 LLM 生成数据，必须公开这一点，并采用多渲染器平均。

### 8.6 题目质量：IRT

- 在所有参照系统及其变体（≥20 个）上拟合 2PL IRT 模型。
- 剔除区分度过低的题（所有系统都对或都错）和区分度为负的题（通常意味着答案键有误）。
- 基于 IRT 构造一个小型子集，用于快速迭代开发，思路同 tinyBenchmarks（Polo et al. 2024）。

### 8.7 裁判验证

- 用人工标注的结果类别作为对照集，要求裁判的 κ ≥ 0.8。
- **植入错误压力测试：** 故意构造陈旧、含糊、编造、张冠李戴四类错误答案，裁判在每一类上的识别率都要 ≥ 90%。LoCoMo 的审计发现，裁判会接受 63% 的含糊错误答案。
- 裁判模型不能与任何被测系统或渲染器相同。

### 8.8 防污染与维护

- **程序化生成：** 测试集由隐藏种子生成，每个版本重新生成；文件内嵌 canary GUID（BetterBench 的一条标准）。
- **公开与隐藏分离：** dev 集公开；test 集只通过提交评测，并限制提交频率。
- **版本管理：** 生成器、渲染提示词、裁判提示词都做版本化。排行榜只在同版本内比较，并设退役机制。

## 9. 统计报告规范

- **分析单位是流**，不是题。报告配对的流级 bootstrap 95% CI，或者使用混合效应模型：`outcome ~ system + (1|stream) + (1|need_type)`。参考 Miller 的 *Adding Error Bars to Evals*。
- **功效估算：**
  - 每条流约 20 个需求，ICC ≈ 0.1，设计效应约 2.9。
  - 要检出二值指标上 5–10pp 的配对差异，大约需要 30–60 条流，这也是 L2 定为 60 条流的依据。
  - 每次报告都要附上最小可检出效应（MDE）。
- **多重比较：** 八个维度加各项消融，用 Holm 校正。
- **预注册：** 提前写明主指标（NTU@2k，T1 赛道）、主比较和 MDE。
- **排行榜的必报项：** 预算档位、离线成本、种子数、CI。没有 CI 的结果不上榜。

## 11. 对 Dynamics-memory 的意义

用 TIDE 评测时，各机制分别对应到：

| 系统机制 | 主要受检维度 | 赛道 |
|---|---|---|
| V 衰减与使用信用 | R（半衰期）、I；白盒报告中的需求校准 | T1、白盒 |
| C/M/A 三池、容量、归档与复活 | R（大 Δ、重要稀有类）、F、E | T1 |
| tension → judge、contested 共同服务 | V、C（honest-contested） | T1 |
| salience | R 按重要度分层 | T1 |
| recall_miss 拉取回路 | Rc | **T3（只能在闭环中评测）** |
| 预算三臂实验（ouroboros §11） | NTU–成本 Pareto 前沿 | T1、T3 |

要在 TIDE 中公平地比较，系统需要补两个接口：快照/只读的 `serve`，以及受预算 B 约束的上下文输出。
